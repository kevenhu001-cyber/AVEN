# ADR-008：按需基础设施与渐进交付

- 状态：已接受（仅契约；按阶段验证）
- 日期：2026-11-10
- 部分取代：[ADR-003](0003-data-runtime.md) 中强制预装所有扩展及延后部署决策的部分；其余 Compose 决策保留
- 相关：[开发计划](../../development/DEVELOPMENT_PLAN.md) · [设计系统](../../design/DESIGN_SYSTEM.md)

## 背景

完整 MVP 同时包含多端、AI、授权匹配和日程。当前开发资源有限，尚无代码；如果先建齐所有基础设施与导航，容易延误真实业务和 UI 验证。规划中的扩展不能自动成为 M0 的启动依赖。

## 决策

1. 保留原规格 18 项 MVP DoD，不把首条确定性闭环称为完整 MVP。先跑通手工资料、真实机会、授权引荐、关系和撤销，再补齐真实 AI、语义匹配、Android 全链路和日程。
2. M0 Compose 必需 PostgreSQL 与 Redis。pgvector 在语义检索前验证并启用；PostGIS 在真实地理查询出现时再决策、安装和迁移。基础迁移不出现尚未启用的 `vector(n)` 列，也不为未使用的扩展制作组合镜像。
3. M0-02 锁定运行时和依赖兼容矩阵，M0-03 才在实际应用中验证构建；应用骨架未存在时不能要求或记录四应用构建通过。Node 采用仍受支持且与框架兼容的 LTS，不因“最新”而盲目升级。
4. M1 增加首条旅程的高保真与可点击原型评审。原型可使用显式样例，但与功能验收分开；未开放模块从常用导航隐藏，不用空 Tab 充当完成。
5. Expo Go 用于早期健康连接与布局；引入自定义原生能力或进入 M5 主线验收前建立 development build，M7 使用实际发布安装包。没有 Android SDK 不阻止记录云构建/真机路径，但构建、安装和设备证据不可省略。
6. M0 确认候选部署地域、网络可达性和预算；M2 前确认生产邮件及认证威胁模型；任何真实试点或真实 Provider 数据发送前确认告知同意、数据位置、保留和处理边界。M7 负责最终复验，不是首次调查。
7. CI 覆盖 `push` 与 PR；按已有实现启用实际检查，不留空绿色脚本。日志与错误处理从首条接口开始，备份与恢复在接纳真实用户数据前演练。

## 备选方案

- 一次搭齐全部扩展与空模块：早期成本高且不能证明价值，不采用。
- 仅做网页演示并取消 Android/隐私验收：缩减原始交付承诺，不采用。
- 只用 Expo Go 或模拟截图宣称移动端可发布：证据不足，不采用。

## 后果与验证

分阶段建立依赖和证据，不改变 API-first、模块化单体和原生移动端方向。每个验证门的负责人与结果在开始任务时记录；当前均未通过。

- [ ] 无 pgvector/PostGIS 的基础迁移可运行；启用扩展有独立迁移与升级验证。
- [ ] 关键页面双端设计经过评审，再进入对应 UI 实现。
- [ ] Expo development build 和发布构建分别有真机记录。
- [ ] 试点前具备部署/邮件网络证据、删除流程、支持渠道和恢复演练。
