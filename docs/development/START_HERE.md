## 2. 先验证哪一条业务链

首条主线选用科研机会引荐：

1. 组织管理员创建组织并发布一条科研机会。
2. 个人填写并确认兴趣、技能、项目经历和寻找需求。
3. 系统在许可范围内检索机会，给出由实际条件支持的推荐理由。
4. 个人查看本次将披露的具体资料、接收方、用途和有效期，确认发送引荐请求。
5. 有权限的组织成员查看获授权的资料，接受或拒绝。
6. 双方接受后，仅建立一个关系空间，展示获授权的共同上下文。
7. 用户撤销授权后，受该授权约束的共享内容停止通过系统访问；同步验证缓存和后续检索。

这条主线同时验证个人上下文、组织资源、匹配、授权和关系建立，是 PAN 的主要价值链。先通过显式表单和确定性业务服务跑通，再接入 AI 对话作为同一套服务的入口。

首条链路通过不等于 MVP 完成。组织 AI、完整记忆管理、原生 Android、日程协调、监控等仍需按原规格交付。

## 3. 技术取舍

沿用原规格的技术方向：pnpm + Turborepo、Next.js、Expo、NestJS 模块化单体、PostgreSQL + Drizzle、Zod、Redis + BullMQ。

- M0 建立 Web、Mobile、API、Worker 的最小可运行骨架；先以 Web 联调首条业务链，随后让 Android 消费相同 API。Android 不是可省略的最终验收项。
- Web 和 Mobile 共享契约、API 客户端、权限定义和设计令牌；分别实现界面。
- Web 的业务数据读写通过 NestJS API；不在 Next.js 中复制一套业务后端。
- 先创建实际需要的包，不一次生成全部空模块。优先 `contracts`、`database`、`api-client`、`design-tokens`、`config`。
- 队列先验证一项真实的异步任务及其失败重试；不将普通 CRUD 全部异步化。
- 初期匹配以真实数据、硬条件过滤和可解释排序为基线；向量检索作为后续增量，明确标记当前能力，不将基线冒充完整智能匹配。
- PostGIS 的业务查询放到地理需求出现时实现；数据库扩展的安装和迁移能力在基础设施阶段检查。
- AI Provider 支持本地 Mock，开发时明确标识。真实模型接入后单独验证效果，不用 Mock 输出证明业务智能已经完成。
- 依赖的具体版本在初始化时查阅官方兼容要求并锁定，不直接根据本机版本推断兼容。

## 4. 编码前需要明确的规则

### 身份与组织权限

选定身份提供方、会话验证方式，以及个人主体和组织操作身份的切换规则。开发测试身份只能用于显式开发环境，不得成为生产鉴权的回退路径。

至少区分组织管理员、普通成员和组织外用户。校园认证状态独立记录；注册或选择学校不等于通过校园认证。

### 数据可见性与授权

原规格的 PRIVATE、DISCOVERABLE、MATCH_ONLY、RELATIONSHIP_SHARED、PUBLIC 应按用途定义权限矩阵，不能直接视为由低到高的枚举等级。

需要逐项定义：本人查看、发现、后台匹配、引荐预览、关系空间读取分别允许哪些字段，由什么有效授权支持。

共享快照必须关联授权和来源版本；读取快照仍检查接收主体、用途、过期和撤销状态。授权撤销不会自动撤销其他独立有效授权，也无法收回接收者此前在系统外保存的内容。

### 状态与并发

分别记录双方决定、引荐流程状态和授权状态，避免用一个布尔值承载全部含义。

明确拒绝、撤回、过期、机会关闭和授权失效时能否继续接受。接受时在事务内重新校验权限和业务条件；用数据库唯一约束与幂等机制防止重复创建关系空间。

组织有多名管理员时，应明确谁可代表组织接受，以及多个成员同时操作时如何避免覆盖。

### AI 行动确认

AI 可以提出草稿，正式发布、发送引荐和共享资料走后端确认流程。确认应绑定草稿内容版本；草稿变化后重新预览，执行时重新校验权限、授权和幂等键。

原规格尚缺授权创建/查询/撤销、行动确认、任务查询和流式恢复的完整 API 契约，需要补充。POST SSE 的客户端需支持请求体、取消和鉴权，并明确事件序号、重连语义；不能假定重连就能安全重放写操作。

## 5. 第一批工作及验收

| 顺序 | 工作 | 验收依据 |
|---|---|---|
| 1 | 补齐最小工程文档 | README 写清启动方式；AGENTS 写清边界；PRD 明确首条旅程；DESIGN_SYSTEM 提取原规格令牌；TDD 明确模块、身份与授权；SCHEMA 明确首批表及约束 |
| 2 | 初始化 Monorepo 和运行环境 | 明确并锁定运行时与包管理器版本；Web、API、Worker、Expo 可启动；数据库和 Redis 可连接；有 `.env.example`；无真实密钥入库 |
| 3 | 建立最小 CI | 实际执行 lint、类型检查、核心测试、迁移检查和构建；缺失的检查不得标为通过 |
| 4 | 实现身份、组织和数据隔离 | 两个个人、两个组织的集成用例证明隔离；应用数据库角色不能绕过 RLS；连接池复用不残留上一请求身份 |
| 5 | 实现个人确认资料与机会发布 | 数据真实持久化；普通成员不能越权发布；私人字段不出现在公开机会或匹配响应中 |
| 6 | 实现引荐、授权和关系空间 | 双方决定独立记录；重复接受只产生一个空间；拒绝、撤回、过期和授权失效有明确行为 |
| 7 | 完成撤销和关键端到端用例 | 撤销后受影响内容不可读取；覆盖缓存、检索、跨组织访问和并发接受 |
| 8 | 加入 AI 入口并接通 Android | AI 调用同一业务服务，展示预览和执行状态；Android 完成同一引荐主线，覆盖断网、重试和安全区域 |

这些是实现依赖顺序，不是工期承诺。M1 的令牌、导航和最小组件随相关页面推进；日程协调在主线稳定后进入实现。

## 6. 首批数据与接口范围

首批持久化实体围绕主线展开：

- 身份：Principal、User、Campus、CampusMembership、Organization、OrganizationMembership。
- 上下文与机会：MemoryItem、MemorySource、Intent、Opportunity。
- 引荐与共享：MatchCandidate、MatchDecision、ConsentGrant、ConsentEvent、Relationship、RelationshipMember、SharedContextItem。
- 可靠性：AuditLog、OutboxEvent。

按模块逐步增加迁移，不一次建齐全部实体。数据库约束、索引、RLS 和运行角色与业务表一起交付；具体表结构在 SCHEMA 中审查。

API 先覆盖本人资料、组织与成员、已确认资料、机会、匹配查询与决定、授权管理、关系空间。统一 `/api/v1` 前缀、Zod 校验、错误结构和请求标识。

审计只保存必要的操作主体、资源、决定、版本和结果，不把私人对话、模型上下文或密钥作为普通日志记录。

## 7. 首轮界面范围

优先交付 Today、My AI、机会列表与详情、引荐确认、组织机会管理与引荐收件箱、最小关系空间。

这些页面必须对接真实接口，并覆盖加载、空、错误、成功、禁用和无权限状态。尚未实现的 Life 等模块不提供伪可用操作。保留原规格的移动导航、黑白中性色、克制强调色和可访问性要求。
